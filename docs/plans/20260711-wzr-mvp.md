# WZR MVP — Hackathon Pipeline Orchestrator

> **WZR** = *WZR's Zen Runtime* (recursive acronym, GNU-style)

## Overview

Build **WZR** — a Go-based pipeline orchestration tool for Sber internal infrastructure.  
Users construct pipelines in a web chat UI one step at a time (skills + MCP calls), get a YAML definition out,  
then run pipelines autonomously via a Qwen Code CLI subprocess (ralphex pattern).  
Single binary ships everything: backend, embedded web UI, embedded skill markdown files.

Key benefits:
- Replaces ad-hoc manual release workflows with repeatable, shareable pipelines
- Hands-free execution: Qwen handles MCP calls and skill tasks autonomously
- **Self-healing**: when a step fails, AI diagnoses the error and proposes a fix — human approves, pipeline continues
- Live narration makes the AI transparent; post-run chat lets teams interrogate what happened
- ROI counter makes business value visible on every run
- Zero deployment complexity: one binary, file-based pipeline store

## Solution Overview

```
[Web UI — HTMX + SSE]
  ├── /creator   — two modes: step-by-step chat OR describe-and-generate
  ├── /dashboard — pipeline list, params form, real-time log + approval + repair buttons
  └── /templates — gallery of pre-built pipelines (browse, clone, run)

[Go backend — net/http stdlib ServeMux]
  ├── GET  /api/skills                          — list embedded skills
  ├── GET  /api/mcps                            — list registered MCP servers + tools
  ├── GET  /api/pipelines                       — list saved pipeline YAMLs
  ├── GET  /api/pipelines/{name}                — get pipeline YAML
  ├── POST /api/pipelines                       — save pipeline YAML
  ├── GET  /api/templates                       — list embedded template YAMLs
  ├── POST /api/templates/{name}/clone          — copy template to pipelines/
  ├── POST /api/creator/message                 — step-by-step: chat turn → suggested next step
  ├── POST /api/creator/generate                — one-shot: prose description → full YAML
  ├── POST /api/pipelines/{name}/run            — start run, returns run ID
  ├── GET  /api/runs/{id}/events                — SSE stream of step events (+ narration lines)
  ├── POST /api/runs/{id}/steps/{step}/approve  — approve/reject approval gate or repair proposal
  ├── POST /api/runs/{id}/chat                  — post-run chat: question → Qwen answers with run context
  └── GET  /api/stats                           — ROI stats: runs count, time saved, success rate

[Pipeline runner — on each step]
  ├── skill/mcp step:   build prompt → Qwen subprocess → stream output lines as narration events
  ├── approval step:    fire awaiting_approval event → block on chan bool with timeout
  └── on step failure:  call Qwen repair prompt → fire repair_suggested event → block on chan bool
                        if approved: execute fix_command → retry step once → continue or fail
                        if rejected/timeout: fire failed event → trigger auto post-mortem

[Self-healing repair flow]
  └── Qwen repair prompt: "Step X failed with: [error]. Return JSON {diagnosis, fix_command}"
      Runner fires repair_suggested event with diagnosis + fix preview
      Human approves → runner runs fix_command via run_sh_command, retries step (max 1 retry)

[ROI tracker]
  └── run_history.json: each completed run logged with pipeline name, duration, manual_minutes estimate
      /api/stats aggregates and returns time saved totals

[MultiNotifier]
  ├── SSENotifier      — pushes all events (step status, narration, repair, chat) to dashboard
  └── SberChatNotifier — POST to SberChat REST API (stub: TODO for team member)

[Qwen Code CLI subprocess]
  └── qwen --approve-mode auto --allowed-tools run_sh_command
      → handles MCP calls, skill execution, repair commands autonomously
```

Key design decisions:
- One Qwen process per step (simple lifecycle, isolated context)
- Raw text output of step N injected as context into step N+1 prompt; also accumulated as run log for post-run chat
- SSE (not WebSocket) for all streaming — narration, step status, repair suggestions, chat responses
- `net/http` stdlib with Go 1.22 pattern matching — no external router dependency
- `Notifier` interface unifies SSE stream and SberChat: runner fires events once, both channels receive them
- Approval gates and repair proposals share the same `ApprovalHub` `chan bool` mechanism
- Self-healing: max 1 repair attempt per step; on second failure → normal fail path → auto post-mortem
- Templates embedded via `go:embed templates/*.yaml`; cloning copies to `pipelines/`
- `manual_minutes` field on pipeline YAML drives ROI counter; stored in `run_history.json`
- Creator has two modes: step-by-step (fine control) and describe-and-generate (speed)

## Technical Details

**Pipeline YAML shape:**
```yaml
name: release-manager
version: "1.0"
params:
  project: ""
  version: ""
steps:
  - id: check-readiness
    name: Check Jira tickets readiness
    type: skill
    skill: check-release-readiness
    params:
      project: "{{ .project }}"
      version: "{{ .version }}"
  - id: verify-prs
    name: Verify Bitbucket PRs merged
    type: mcp
    server: bitbucket
    tool: list_pull_requests
    params:
      state: open
  - id: trigger-build
    name: Trigger Jenkins build
    type: mcp
    server: jenkins
    tool: trigger_build
    params:
      job: "release/{{ .project }}"
    depends_on: verify-prs
  - id: update-docs
    name: Update Confluence release notes
    type: skill
    skill: update-release-notes
  - id: confirm-deploy
    name: Confirm deployment to staging
    type: approval
    timeout_minutes: 30

  - id: close-tickets
    name: Transition Jira tickets to Released
    type: mcp
    server: jira
    tool: transition_issues
    params:
      target_status: Released
on_failure:
  notify: "Pipeline {{ .name }} failed at step {{ .failed_step }}: {{ .error }}"
manual_minutes: 100   # manual effort estimate — drives ROI counter
```

**Step prompt template sent to Qwen:**
```
You are executing step "{{ step.name }}" ({{ step.id }}) in pipeline "{{ pipeline.name }}".

{% if prev_output %}
Context from previous step:
{{ prev_output }}
{% endif %}

Your task:
{{ if skill }}
Use the following skill and execute it autonomously:
{{ skill_content }}
With parameters: {{ params_json }}
{{ else }}
Call MCP server "{{ step.server }}", tool "{{ step.tool }}" with these parameters:
{{ params_json }}
Report what you did and the result.
{{ end }}
```

**StepEvent shape (shared by SSE and SberChat):**
```json
{
  "run_id": "abc123",
  "pipeline": "release-manager",
  "step_id": "verify-prs",
  "step_name": "Verify Bitbucket PRs merged",
  "status": "running|success|failed|awaiting_approval|repair_suggested|narration|postmortem",
  "output": "...",
  "error": "",
  "diagnosis": "",
  "fix_command": "",
  "ts": 1234567890
}
```
- `narration` events carry incremental Qwen output lines (live commentary while step runs)
- `repair_suggested` events carry `diagnosis` and `fix_command` for the repair UI card
- `postmortem` event carries the full post-mortem text after a terminal failure
